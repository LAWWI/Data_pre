3. การปรับ scale คอลัมน์ Time และ Amount

Amount — log1p แล้วตามด้วย RobustScaler

  • Amount เบ้ขวาจัด (skew 16.978) มีรายการยอดสูงผิดปกติจำนวนมาก จึงใช้ log1p ลดความเบ้ก่อน
  • ตามด้วย RobustScaler ที่อิง median และ IQR ทนค่า outlier ได้ดีกว่า StandardScaler
  • ค่าที่ fit ได้จาก train: center = 3.139, scale (IQR) = 2.4669

Time — StandardScaler

  • ค่าดิบเป็นวินาทีนับจากธุรกรรมแรก (0 ถึง 48 ชม.) สเกลใหญ่กว่า V1–V28 หลายพันเท่า จึงบีบให้ mean = 0, std = 1
  • ค่าที่ fit ได้จาก train: mean = 94,900.22, std = 47,488.11
  • เพิ่ม Hour_sin / Hour_cos เพื่อเก็บพฤติกรรมตามช่วงเวลา และทำให้ 23:00 กับ 00:00 อยู่ใกล้กันในเชิงตัวเลข
ป้องกัน data leakage: scaler ทั้งสองตัว fit จาก train set เท่านั้น แล้วจึง transform ลง test set ไม่ให้สถิติของ test รั่วเข้าสู่กระบวนการเทรน

คอลัมน์ที่ตัดออกหลังแปลง: Time, Amount, Amount_log
ฟีเจอร์ที่เพิ่มเข้ามา: Hour_sin, Hour_cos, Amount_scaled, Time_scaled รวมกับ V1–V28 เดิม = 32 ฟีเจอร์

5. ผลตรวจสอบด้วยโมเดล (LogisticRegression)

วิธีRecallPrecisionF1ROC-AUCPR-AUCจับโกงได้False alarm
1) ไม่แก้ imbalance0.60.85070.70370.95370.696157/9510
2) class_weight=balanced0.87370.05570.10470.96650.680683/951407
3) SMOTE0.86320.10760.19140.96510.665682/95680

แถวที่ไฮไลต์คือวิธีที่ได้ PR-AUC สูงสุด (1) ไม่แก้ imbalance) แต่ต้องอ่านตารางนี้สองชั้น:

  • PR-AUC ใกล้กันทั้งสามวิธี (0.6656–0.6961) เพราะเป็นค่าที่วัด “การเรียงลำดับความเสี่ยง” ซึ่ง rebalance ไม่ได้เปลี่ยนมากนักสำหรับ LogisticRegression
  • สิ่งที่ rebalance เปลี่ยนจริงคือ จุดตัดสินใจ (threshold ภายใน): recall ขยับจาก 0.6 เป็น 0.8737 (balanced) และ 0.8632 (SMOTE) คือจับการโกงได้เพิ่มจาก 57 เป็น 83 จาก 95 รายการ
  • ราคาที่จ่ายคือ false alarm เพิ่มจาก 10 เป็น 1407 รายการ (precision ลดลง) — ในงานจับโกงมักยอมแลก เพราะ false negative แพงกว่ามาก
ข้อเสนอแนะต่อ: ใช้ข้อมูลที่ pre-process แล้วไปต่อกับ XGBoost / LightGBM โดยตั้ง scale_pos_weight (ทำหน้าที่เดียวกับ balanced mode) แล้วจูน threshold จาก precision–recall curve ให้ตรงกับต้นทุนธุรกิจ จะได้ผลดีกว่าการเลือกเพียงวิธี rebalance อย่างเดียว
